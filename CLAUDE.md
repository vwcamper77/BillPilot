# ClearTill — product rules (do not violate)

ClearTill is a calm, payday-aware cashflow heads-up. It answers ONE question:
"Am I clear till payday?" Everything serves that.

NEVER build: Open Banking / bank linking, spend categorisation or budgeting,
loans / credit / BNPL, ads. Manual balance snapshot in, forecast out.

Every screen: show the ANSWER and the ACTION. Hide the arithmetic one tap away.
- Home = ONE hero answer + 3 quiet supporting numbers + everything else as tappable rows.
- Never show intermediate workings (shortfall maths, "£X/day more than runway allows")
  as top-level tiles. Conclusion + next step only.

Voice: calm, practical, like a sharp PA. No jokes, no exclamation marks,
no "shortfall/pressure/still need" panic language, no financial advice.

When in doubt, REMOVE. "Too cluttered" is the problem, never "too sparse."
## Commands

```bash
npm run dev      # Start dev server (http://localhost:3000)
npm run build    # Production build — run this after every change to catch errors
npm run start    # Start production server after build
```

There are no tests or linters configured. `npm run build` is the only correctness gate — always run it before committing.

## Environment variables

Copy `.env.example` to `.env.local`. Two sets of Firebase credentials are needed:

- **Client** (`NEXT_PUBLIC_FIREBASE_*`) — used in browser via `lib/firebase.js`
- **Admin** (`FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`) — used in API routes via `lib/firebaseAdmin.js`
- **OpenAI** (`OPENAI_API_KEY`) — required for the chat/image parser; falls back to Tesseract OCR when GPT-4o fails
- **Cron** (`CRON_SECRET`) — `Authorization: Bearer <secret>` header required on `/api/reminders`
- **Admin** (`ADMIN_EMAILS`) — comma-separated allowlist for `/admin/analytics`, separate from `FOUNDING_ACCESS_ADMIN_EMAILS`

## Architecture

### Pages

| Route | File | Notes |
|---|---|---|
| `/` | `app/page.jsx` | Static landing page |
| `/dashboard` | `app/dashboard/page.jsx` | Main app (~3 000+ lines, single component) |

### The dashboard component (`app/dashboard/page.jsx`)

This is a monolithic `"use client"` component. Everything lives inside or just above `DashboardPage`:

- **Module-level helpers**: `isRecentlyAdded`, `classifyBill`, `CATEGORY_META`, `TRACKER_CHECKS`, `LARGE_COST_CATEGORY_META`, `BillPagination`, `BillGroup`, `HouseholdTracker`, `BillCategoryPill`
- **Module-level constant**: `BILLS_PER_PAGE = 6`
- **All Firestore subscriptions** are `onSnapshot` listeners set up inside `useEffect` — bills, income, balance/account, reminders, large costs, savings
- **All derived state** is `useMemo`: `dashboard` (from `calculateDashboard`), `allBillsForList`, `pagedBills`, `sortedLargeCosts`, etc.
- **Bill list pagination state**: `billListPage` (number) + `billListFilter` ("all" | "before" | "after" | "recent") — filter changes reset page to 0 inline in `onClick`

### Firestore data model

All data is per-user under `users/{userId}/`:

| Collection/doc | Contents |
|---|---|
| `settings/balance` | `currentBalance`, `currency` |
| `income/main` | `payDay` (1–31), `amount`, `currency` |
| `bills/{billId}` | `name`, `amount`, `dueDay`, `nextDueDate`, `reminderDate`, `category` (null = auto-detect), `createdAt` |
| `reminders/{billId}_{date}` | Generated by `/api/reminders` cron |
| `largeCosts/{costId}` | `name`, `amount`, `dueDate`, `frequency`, `category`, `amountAlreadySaved` |
| `settings/savings` | `currentBalance` (general savings pot) |

### `lib/billMath.js`

Pure calculation library shared by both client pages and API routes. Key exports:

- `calculateDashboard(bills, income, account, todayIso)` — returns `beforePayday`, `afterPayday`, `runwayEvents`, `leftBeforePayday`, `dailyLimitTillPayday`, etc.
- `calculateLargeCostImpact(costs, generalSavings, baseDailyBudget, daysTillPayday)` — per-day reserve math for large costs
- `buildBillDocument`, `buildIncomeDocument`, `buildLargeCostDocument` — normalise + schedule before Firestore write
- `getTodayIso()` — always returns today in `Europe/London` timezone as `YYYY-MM-DD`
- All date arithmetic uses ISO strings (`YYYY-MM-DD`), never raw `Date` objects, to avoid timezone drift

### API routes

**`/api/parse`** — NLP/vision parser called by the chat input on the dashboard:
1. Tries a regex quick-parse first (no OpenAI call)
2. Calls GPT-4o-mini with a structured JSON prompt
3. Falls back to Tesseract OCR (`tesseract.js`) if GPT-4o fails or returns nothing
- Two modes: chat (single bill/income) and image-import (bulk extraction from screenshots)
- `eng.traineddata` must be present at the repo root for Tesseract to work locally

**`/api/reminders`** — Vercel cron (runs 07:00 UTC daily, configured in `vercel.json`):
- Requires `Authorization: Bearer <CRON_SECRET>` header
- Walks all users' active bills, writes `reminders/{billId}_{date}` docs for bills due the next day
- Accepts `?uid=` query param in non-production to target a single user

### Auth

Anonymous sign-in on first visit; users can upgrade to Google or email/password (`linkWithPopup`). `authPersistenceReady` is awaited before any Firestore read so auth state is stable.

### Admin analytics (`/admin/analytics`)

Internal-only acquisition/funnel dashboard, gated by `ADMIN_EMAILS` (checked via `lib/adminAuth.server.js`). Three top-level, server-only Firestore collections — never touched by the client SDK, so `firestore.rules` doesn't need to know about them:

| Collection | Written by |
|---|---|
| `analyticsEvents/{autoId}` | `lib/customerProfile.server.js`'s `recordAnalyticsEvent()`, called from `/api/track` and the Stripe webhook |
| `customers/{uid}` | Denormalized read-model keyed by Firebase uid — created on `account_created`, updated by `touchCustomerActivity()` from bill/settings/forecast routes and the Stripe webhook |
| `adSpend/{autoId}` | Manually entered by admins via `/api/admin/ad-spend` |

`app/api/track/route.js` is the one intentionally public, unauthenticated-capable write endpoint in the app — most funnel events (`landing_page_view`, `hero_cta_clicked`, `signup_started`) happen before any Firebase user exists. Don't "fix" it by requiring a Bearer token; `account_created` is the one event that does require one.

Client-side event firing goes through `trackEvent()` in `lib/analytics/track.js` (fire-and-forget, mirrors `lib/security/clientSecurity.js`'s pattern). First-touch UTM/referrer attribution is captured once per browser by `lib/analytics/attribution.js` into `localStorage`, and attached to the `customers/{uid}` doc at `account_created`.

`customers.totalPaid` is stored in pence (Stripe/billing convention); `adSpend.spend` is entered in whole pounds — the aggregation route (`app/api/admin/analytics/route.js`) converts pence→pounds before combining them for CAC/ROAS/ARPU. Stripe checkout is currently one-time-payment only (no subscriptions), so MRR/trial KPIs render "N/A" rather than a fabricated number.

e2e coverage: `tests/e2e/admin-analytics.spec.js` (run via `npm run test:e2e`). Seeds test users and a sample customer via `tests/e2e/setup/seedTestUsers.mjs`, and uses a dev-only `window.__cleartillTestSignIn` hook (`components/TestAuthBridge.jsx`, never mounted in production) to sign into a real browser session as a specific seeded Firebase user without a real OAuth flow.
